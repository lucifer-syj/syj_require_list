# 升级日志：软删除与双窗口架构

**升级日期**：2025-12-22
**版本**：v0.2.0
**类型**：重大功能升级

## 升级概述

本次升级实现了待办管理系统的双窗口架构和软删除机制，主要包括：

### 核心功能
1. **软删除机制**：删除操作不再物理删除数据，而是标记为已删除
2. **回收站功能**：提供回收站查看和管理已删除的待办
3. **双窗口架构**：新增"所有待办"窗口，支持查看所有待办和回收站
4. **窗口间同步**：使用事件系统实现多窗口实时数据同步
5. **主窗口过滤**：主窗口只显示未完成且未删除的待办

### 技术亮点
- 数据库向后兼容的迁移方案
- Vite 多页面应用配置
- Tauri 多窗口管理
- 事件驱动的数据同步机制

## 数据库变更

### 新增字段

在 `todos` 表中添加了两个新字段：

| 字段名 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `is_deleted` | INTEGER | 0 | 软删除标记（0=未删除，1=已删除） |
| `deleted_at` | TEXT | NULL | 删除时间（格式：YYYY-MM-DD HH:MM:SS） |

### 索引创建

```sql
CREATE INDEX IF NOT EXISTS idx_todos_is_deleted ON todos(is_deleted);
```

### 迁移说明

- 使用 `ALTER TABLE` 添加字段，通过 `.ok()` 忽略错误（字段可能已存在）
- 现有数据自动设置 `is_deleted = 0`（未删除）
- 完全向后兼容，不影响现有数据

**实施位置**：`src-tauri/src/lib.rs:init_database()`

## 后端改动

### 修改的命令

#### 1. `get_todos` 命令
**文件**：`src-tauri/src/commands.rs`

**变更**：
- 添加 `include_deleted: Option<bool>` 参数
- 根据参数决定查询已删除或未删除的待办
- 查询语句中添加 `is_deleted` 和 `deleted_at` 字段

**查询逻辑**：
```rust
// 未删除的待办（默认）
WHERE is_deleted = 0 ORDER BY is_completed ASC, id DESC

// 已删除的待办（回收站）
WHERE is_deleted = 1 ORDER BY id DESC
```

#### 2. `delete_todo` 命令
**文件**：`src-tauri/src/commands.rs`

**变更**：从物理删除改为软删除

**原逻辑**：
- 查询关联图片
- 删除图片文件
- 执行 `DELETE FROM todos WHERE id = ?`

**新逻辑**：
- 获取当前时间
- 执行 `UPDATE todos SET is_deleted = 1, deleted_at = ? WHERE id = ?`
- 图片文件保留（只有物理删除时才删除）

### 新增的命令

#### 1. `permanent_delete_todo` 命令
**文件**：`src-tauri/src/commands.rs`

**功能**：物理删除待办（仅在回收站中使用）

**逻辑**：
1. 查询所有关联的图片路径（`todo_images` 表）
2. 查询旧的 `image_path` 字段（向后兼容）
3. 删除所有图片文件
4. 执行 `DELETE FROM todos WHERE id = ?`

#### 2. `restore_todo` 命令
**文件**：`src-tauri/src/commands.rs`

**功能**：从回收站恢复待办

**逻辑**：
```rust
UPDATE todos SET is_deleted = 0, deleted_at = NULL WHERE id = ?
```

### 命令注册

**文件**：`src-tauri/src/lib.rs`

在 `invoke_handler!` 中添加：
```rust
commands::permanent_delete_todo,
commands::restore_todo,
```

## 事件系统

### 事件类型

| 事件名 | 触发时机 | 携带数据 | 监听窗口 |
|--------|----------|----------|----------|
| `todo-deleted` | 软删除待办时 | `{ id: number }` | 主窗口、all-todos 窗口 |
| `todo-restored` | 恢复待办时 | `{ id: number }` | 主窗口、all-todos 窗口 |
| `todo-permanent-deleted` | 物理删除待办时 | `{ id: number }` | 主窗口、all-todos 窗口 |

### 同步机制

1. **发送事件**：在 Store 的方法中，执行操作后发送事件
2. **监听事件**：在各窗口的 `onMounted` 中监听事件
3. **更新数据**：收到事件后调用 `fetchTodos()` 重新加载数据

## 功能说明

### 主窗口行为变更

**变更前**：显示所有待办（包括已完成和未完成）

**变更后**：只显示未完成且未删除的待办

**过滤条件**：`!todo.isCompleted && !todo.isDeleted`

### 所有待办窗口

**打开方式**：点击主窗口底部的"查看所有"按钮

**窗口特性**：
- 尺寸：1024x768
- 单例模式：重复点击显示已有窗口
- 可拖动、可调整大小
- 无边框、半透明背景

**选项卡**：
1. **待办列表**
   - 显示所有未删除的待办（包括已完成和未完成）
   - 显示创建时间和完成时间
   - 支持切换完成状态
   - 支持删除（软删除）

2. **回收站**
   - 显示所有已删除的待办
   - 显示创建时间和删除时间
   - 支持恢复（移回正常列表）
   - 支持永久删除（需二次确认）

### 软删除 vs 物理删除

| 操作类型 | 触发位置 | 数据库操作 | 图片文件 | 可恢复 |
|---------|---------|-----------|---------|--------|
| 软删除 | 主窗口、待办列表 | UPDATE `is_deleted = 1` | 保留 | ✅ |
| 物理删除 | 回收站 | DELETE | 删除 | ❌ |

## 使用指南

### 删除待办

1. 在主窗口或"所有待办"窗口的待办列表中点击"删除"按钮
2. 待办被标记为已删除，移入回收站
3. 图片文件保留

### 查看回收站

1. 点击主窗口底部的"查看所有"按钮
2. 切换到"回收站"选项卡
3. 查看所有已删除的待办

### 恢复待办

1. 在回收站中找到要恢复的待办
2. 点击"恢复"按钮
3. 待办恢复到正常列表

### 永久删除

1. 在回收站中找到要永久删除的待办
2. 点击"永久删除"按钮
3. 确认删除操作
4. 待办和关联的图片文件被永久删除

## 技术细节

### 关键实现点

1. **数据库迁移的向后兼容性**
   - 使用 `.ok()` 忽略 ALTER TABLE 错误
   - 现有数据自动设置默认值

2. **多页面应用配置**
   - Vite 配置多入口点
   - Tauri 窗口配置 `url` 属性

3. **窗口管理**
   - 使用 `Window.getByLabel()` 获取预配置窗口
   - 使用 `hide()`/`show()` 控制显示（单例模式）

4. **事件系统**
   - 使用 Tauri 的 `emit` 和 `listen` API
   - 实现窗口间解耦的数据同步

5. **图片文件管理**
   - 软删除时保留图片文件
   - 物理删除时才删除图片文件
   - 避免数据丢失

### 注意事项

1. **首次运行**：数据库会自动添加新字段，无需手动迁移
2. **软删除的图片**：软删除的待办关联的图片文件会保留，直到永久删除
3. **窗口单例**：all-todos 窗口使用单例模式，不会创建多个实例
4. **事件同步**：窗口间通过事件系统同步，无需手动刷新

### 已知限制

1. **时间显示**：当前显示完整时间字符串，未实现相对时间（"2小时前"）
2. **批量操作**：回收站暂不支持批量删除或批量恢复
3. **搜索功能**：所有待办窗口暂不支持搜索

## 升级影响

### 用户体验变化

1. **主窗口更简洁**：只显示未完成的待办，减少视觉干扰
